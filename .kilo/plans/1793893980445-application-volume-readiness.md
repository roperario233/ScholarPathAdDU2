# Application Volume Readiness Plan

## Scope and Decisions

- Target: import 1,000+ workflow-valid applications at `Submitted`, for existing student profiles and scholarship rows, then support more than 100 concurrent authenticated users. A valid seed must include the application child records required by the normal submission/review workflow; do not treat application-only rows as real submissions.
- Student owners are provisioned separately before the application import. The importer must not create Auth users or profiles; it fails preflight unless every owner exists and the supplied cohort is large enough. The 28 current live profiles include non-students and are not sufficient evidence that 1,000 operational cases can be represented.
- The current live project (`xzptlibbavjswlbgjckx`) is on the Free plan, at migration head `20261063000000`, with exactly 28 profiles and 0 applications, 0 documents, and 0 application-document links. Its current data is not a representative load baseline. Do not run load tests or an experimental seed against it.
- `supabase/config.toml` explicitly sets local `api.max_rows = 1000`; local pooler is disabled and the local auth config allows 30 sign-in/sign-up requests and 150 refreshes per five minutes. These are local settings, not proof of hosted-project limits: inspect hosted API, pooler, and Auth settings before choosing load-test ramp and concurrency.
- Local config points `db.seed.sql_paths` at `./seed.sql`, but no `supabase/seed.sql` exists. Use a dedicated, resumable operator import workflow for this operational dataset; do not use `db reset` or treat a local database-reset seed as a production import path.
- The working tree already has an unrelated user edit in `src/components/StatisticsWorkspace.jsx`; preserve and inspect it before implementing statistics changes.

## Verified Bottlenecks and Risks

- `src/lib/supabaseData.js:281-535` loads all visible applications and documents and several other tables with no `.range()`/`.limit()`. There is no `.range()` call in `src/`. PostgREST's configured row cap (commonly 1,000) can silently truncate older queue rows and document records.
- `loadSupabaseWorkspace()` fetches child slices using the complete application-ID set. At 1,000 rows, UUID lists can exceed practical URL limits. After the initial `Promise.all`, up to eight dependent query stages are awaited sequentially.
- `src/App.jsx:644-681` reloads the entire workspace every 15 seconds and on focus. All server data is then serialized to localStorage by `src/App.jsx:432-434`; quota errors are uncaught. Refresh replaces large arrays (`src/lib/workspaceRefresh.js`), invalidating derivations even when data is unchanged.
- `getLinkedDocuments()` (`src/lib/applicationRequirements.js:650-654`) repeatedly scans all documents. `DepartmentReviewView` renders the full scope; results release has repeated linear lookups and a sequential per-application release loop (`src/App.jsx:2811-2855`); interview conflict detection has nested application/panel scans; workbook generation is synchronous.
- The live application indexes include the primary key and single-column `student_id` and `scholarship_id`, but no index tailored to queue status/date ordering. Existing indexes already cover many child-table foreign keys; add indexes only after measuring the exact filtered queries with RLS enabled.
- Additional verified hot-path gaps: no application `status`/`updated_at`/`submitted_at` queue indexes; no `documents(verification_status, uploaded_at)` index; no `notifications(profile_id, created_at)` ordering index; and `notification_email_log(source_key, user_id)` cannot efficiently serve a `user_id`-only read. `results_releases.application_ids` is an unindexed UUID array used by per-application `ANY` checks.
- `results_releases` currently has a `SELECT` RLS policy equivalent to `USING (true)`, and the workspace loads the full release rows for every role. Besides payload growth, every authenticated user can read release rows and covered application IDs. Constrain access without breaking the student's own held-result masking.
- The database's `enforce_student_application_update()` trigger returns early for callers whose `current_profile_role()` is not `student`. A privileged import can therefore bypass student submission validation. Status log and notification triggers are after-update triggers, so a direct insert at `Submitted` will not automatically create initial status history or send a status notice.
- Current Supabase JS (`^2.110.0`) already has transient PostgREST retries by default. Avoid layering broad retries over it: Supabase documentation warns excess retries can exhaust the Data API connection pool. Retry additional writes only when their idempotency is guaranteed.
- Notification/reminder paths have the same unbounded-volume problem: the deadline worker loads capped whole application and delivery-ledger tables and does linear searches inside recipient loops; release notifications use large UUID `.in()` filters and sequential recipient sends. Several delivery-ledger upserts omit their `(source_key,user_id)` conflict target, and server-created deadline reminders omit a source key, so retries/deduplication are unreliable. Notification HTTP clients have no timeout/backoff, and DB status triggers enqueue a `pg_net` HTTP call per changed application.
- Application updates run a large trigger set, including status history, financial snapshot, offer creation and multiple notification hooks; a bulk status update still executes triggers per row. The history trigger scans the growing timeline JSON array, and release/closing batches can enqueue one `pg_net` request per changed case. Budget and observe this write amplification rather than assuming one SQL statement means one unit of work.
- Performance Advisor findings were read in context: five later-added audit/actor foreign keys remain unindexed; `auth_rls_initplan` and multiple-permissive-policy warnings exist, but the latter reflects intentional role lanes. No security advisor findings were returned. Unused-index and missing-PK warnings relate to the empty seed-scale dataset/backups and are not reasons to drop useful indexes or alter backup tables.

## Prioritized Implementation

### P0 - Establish a Safe, Representative Target and Import Contract

1. Create an isolated staging project/branch with the production schema, RLS, Edge Functions, storage configuration, and an appropriately sized plan/compute profile. Use generated/anonymized test identities and document bytes there; do not copy real student files or financial/profile PII to staging. Establish backups/restore checks before loading. Record actual hosted database/API/auth/storage limits (including `db-max-rows`, pooler/connection limits and Auth token-refresh/sign-in limits) and use the staging project for all seed and load-test runs; select production capacity from measured results, not the current Free project's empty tables. Pace test-account sign-ins so Auth rate limits do not distort the API workload.
2. Define the seed manifest: stable source-row ID, already-provisioned `profiles.user_id`, `scholarships.id`, explicit `submitted_at`, Submitted application fields, complete versioned profile snapshot, statement/certification/time fields, financial answers plus the frozen `financial_snapshot`, required current proof files and attachment links. Require all document objects to exist in the private Storage bucket and be owned by the referenced student. Documents enter `Pending`; do not fabricate a verification decision or actor. Reject invalid/non-student owners, out-of-scope tracks, duplicate source IDs, duplicate/conflicting cases, incomplete profile/financial answers, missing files, stale proofs, and invalid status/date combinations before production visibility. Validate deadline/active-track eligibility as of the declared submission date for historical cases; do not reject a previously valid Submitted case only because its scholarship deadline has since passed or its current profile answer changed from the frozen snapshot.
3. Add a restricted, audited import path rather than using browser writes or a blind service-role bulk insert. Implement a Node operator script under `scripts/` plus a database migration for a private import-batch/source ledger and an operator-only RPC. Pin `search_path`, revoke execute from public/authenticated, grant only to the server-side import identity, and keep service-role credentials out of the frontend. Stage and validate the whole manifest first; upload storage objects to deterministic paths with bounded concurrency; then commit complete application graphs in retryable chunks (initially 25-100 cases, bounded by payload size) inside transactions. Keep a row-level source key/hash so reruns are idempotent and changed content is detected rather than silently overwritten.
4. The finalization path must explicitly reuse or mirror the existing submission gates (`missing_application_profile_item()`, required-document/current-proof logic, and `financial_answers_complete()`); it must not rely on the trigger's non-student early return. For historical cases, evaluate answers/proofs against the frozen application snapshot and `submitted_at` proof context. Because the submit-time financial snapshot trigger runs on update, explicitly populate and verify `application_financial_details.financial_snapshot` during the import insert. Insert the initial `Submitted` application status-log row as a system/import event in the same transaction, preserve the timeline snapshot, and do not send duplicate submit emails/SMS or notifications for historical cases. A failed chunk remains invisible or quarantined until complete; report per-row validation and insert errors, checkpoint successful chunks, and retain a cleanup manifest for orphaned Storage objects. Never disable constraints, RLS, or triggers globally.
5. Reconcile imports after each batch: source rows versus committed rows, foreign keys, one initial status-history row per case, current required attachments, storage object existence, RLS visibility for student/Admin/Staff/reviewer roles, no duplicate notifications, and no malformed/missing snapshot fields. Record counts and checksums without logging personal data.

### P0 - Bound Reads and Refreshes Before Exposing 1,000 Rows

1. Replace whole-workspace application hydration with query functions in `src/lib/supabaseData.js` for role-scoped, explicitly selected application pages. Use stable keyset pagination (timestamp plus `id` tie-breaker; filters/order applied in Postgres) for the Intake Pool, Review Queue, Department Review, student Applications, Results Release, interviews and any other unbounded list. Start with 50 rows/page and tune; fetch exact/estimated counts separately only where shown. Do not raise the API row cap to make unbounded selects appear complete. Keep RLS authoritative and preserve the central `reviewer_scopes_to_student()` boundary.
2. Keep application details lazy: fetch attached documents, status history, review comments, interview panel/notes, finances and grant/offer details for the visible page or opened case, not every case on every session. Remove 1,000-ID `.in()` requests; if a page needs a related slice, cap it to that page or use a scoped server query/RPC. Keep status-log, comment, note, document and offer data behind the existing role checks.
3. Change `loadSupabaseWorkspace()` and `src/App.jsx` refresh to load compact role-appropriate summaries and the current page only. Replace 15-second full snapshots with single-flight, cancellable, jittered page/delta refreshes; refresh only while visible, avoid duplicate focus/poll requests, and use a cheap server count for navigation badges. Preserve the current behavior that ignores stale responses after account changes.
4. Stop persisting server-backed collections (all applications/documents/profiles/status and staff workflow slices) in the whole app-state localStorage record. Persist only intended device preferences/local-only state and unsynced drafts; add a backwards-compatible state migration that drops bulky server snapshots but keeps theme, notification preferences, custom deadlines and other supported local preferences. Guard storage quota failures and verify sign-out/account isolation.

### P0 - Preserve Release Privacy and Workflow Authority

1. Replace the `results_releases` authenticated-wide-open `SELECT` policy with role-aware access: Admissions Office access per current rules, reviewer access only to releases covering in-scope cases, and a student read only when the release covers that student's own application. Preserve held-result masking and test all role cases under RLS.
2. Normalize `results_releases.application_ids` to a coverage join table keyed by `(release_id, application_id)` (backfill existing release coverage, update release RPCs and readers, then retire array-based policy/query paths). This makes student/reviewer scope checks indexable and avoids large arrays in every workspace payload. If the migration is not viable in the measured scope, use a GIN index as an interim measure, but still fix the RLS leak and stop loading all release rows to all roles.
3. Keep `reviewer_scopes_to_student()` as the single authorization predicate. Measure its per-row cost with 1,000 in-scope applications/documents under reviewer RLS; optimize call shape or a scoped server query only if it is a measured bottleneck, with unchanged SQL/client scope semantics and explicit tests for Dean/Assistant Dean/Chairperson/Interviewer boundaries.
4. Evaluate `auth_rls_initplan` findings by changing direct `auth.uid()` policy expressions to `(select auth.uid())` only on policies where explain plans show repeated evaluation. Do not mechanically merge permissive role policies: their OR-composed Admin/Staff/student/reviewer lanes encode required security boundaries. Ignore the advisor's no-primary-key warnings on `backups.reset_*` snapshots and do not drop indexes reported unused against the current empty application dataset.

### P1 - Query Plans, Indexes, and Expensive Derivations

1. On staging with representative rows, capture `EXPLAIN (ANALYZE, BUFFERS)` for each real paginated query both with RLS as each role and for its aggregate counterpart. Review Supabase Performance Advisor, `pg_stat_statements`, sequential scans, blocking and pool/connections. Candidate workload indexes to validate include `applications(status, submitted_at, id)` for intake; `applications(updated_at DESC, id)` for recent lists; `applications(student_id, updated_at DESC, id)` and `applications(scholarship_id, status, submitted_at)` for owner/track queues; `documents(owner_id, uploaded_at DESC, id)` plus a partial verification-status index for review queues; `notifications(profile_id, created_at DESC)`; `notification_email_log(user_id)`; and `custom_deadlines(deadline)` for reminder scans. Prefer partial/composite indexes that match real filters, not a stack of speculative single-column indexes. Separately add the five inexpensive uncovered FK indexes reported by the advisor: `application_grant_amounts(set_by)`, `application_waitlist_ranks(set_by)`, `scholarship_offers(responded_by)`, `support_messages(sender_id)`, and `support_messages(replying_to_id)`. Update `supabase/schema.sql` and run `ANALYZE` after the seed.
2. Move volume-only statistics, dashboard counts, and stage totals from downloading every application to role- and scope-aware SQL aggregates/RPCs. Staff must still receive volume-only counts; reviewer aggregates must use the same scope predicate; never aggregate or export sensitive finance or named student data beyond existing role access.
3. Build page-local `Map`s keyed by document/application ID for linked documents, offers, waitlist ranks, interview notes and panelists; memoize stable selectors. Convert `findRosterConflicts()` to interval/resource grouping plus a sweep-line algorithm rather than nested scans. Memoize/reduce final-check sibling hints and calendar/status-event derivations. Render bounded pages; add virtualization only if measured page DOM still needs it.
4. Make large applicant/statistics workbook generation non-blocking (worker or chunked generation) and bound export size/filters. Keep export authorization, staff-only fields, and frozen snapshot semantics unchanged.

### P1 - Bulk Operations, Idempotency, and Failure Recovery

1. Replace `releaseScholarshipResults()`'s sequential per-application updates with a database batch RPC that accepts a bounded set of IDs and an idempotency key, locks and revalidates each application, enforces current final-check/offer rules, and returns per-case results. Preserve existing workflow authority, release rows, status history, offer creation and student-facing hold behavior; never turn a bulk operation into a status-policy bypass.
2. Ensure bulk release notification fan-out is bounded and retryable. Preserve stable `application-status-<id>-<status>` source keys and channel-specific delivery semantics; use a durable outbox/worker with capped concurrency if measured `pg_net`/Edge Function fan-out overwhelms the service. The import path itself must not trigger status notifications.
3. Use one bounded concurrency/backpressure policy for importer DB chunks and Storage uploads. Honor `Retry-After`; retry only network/408/429/5xx/transient failures with exponential backoff and jitter, and never retry validation, authorization, or constraint errors. Existing SDK retries remain the baseline for eligible PostgREST requests; do not add global fetch retries. Persist checkpoints and a failed-row report so operator reruns resume safely.
4. Improve UI error handling: retain last-good page data on transient refresh errors, show recoverable stale/error state and manual retry, distinguish validation/permission/conflict/rate-limit/server errors, and prevent double-submit/release clicks while pending. Use `Promise.allSettled` for independent slices so one optional/missing slice does not blank a whole page. Keep logs free of names, emails, profile snapshots, document paths, and financial details.

### P1 - Make Scheduled and Notification Work Bounded

1. Fix `process-deadline-reminders` before the new cohort can be included: paginate applications, scholarships, custom deadlines and deliveries; query only candidate delivery keys instead of loading the whole ledger; replace repeated `.find()`/`.filter()` with keyed maps; correct terminal/Draft status selection; and checkpoint a cursor so a run resumes. Isolate failures per reminder so one bad profile/send does not abort the rest.
2. Repair delivery idempotency: set `onConflict: 'source_key,user_id'` on every intended ledger upsert and check write errors; add stable source keys to server-created in-app reminders; avoid unbounded delivery-ledger reads. Add an append-only delivery-attempt record (or equivalent attempt history) with channel, status, attempt time/count and correlation key; keep the current delivery ledger as the latest per-channel state if needed.
3. Add HTTP timeouts, capped concurrency, `Retry-After` handling, and exponential backoff with jitter for Resend/iprogSMS. Retry only channels/operations with safe idempotency. SMS has no provider idempotency and only confirms queue acceptance: do not automatically repeat an ambiguous timed-out SMS submission unless a provider status check proves it was not accepted. Preserve the existing database-only SMS caller and avoid presenting queue acceptance as carrier delivery.
4. Page the results-release notification worker and persist per-applicant progress so a release of 1,000+ cases resumes rather than aborting at the first failure. Bound the application's status-trigger fan-out through a durable outbox/worker; do not enqueue thousands of `pg_net` requests in one transaction. Preserve stable source keys and the existing email/in-app/SMS channel semantics.
5. Add structured, PII-free Edge Function logs with batch/release/source IDs, channel outcome, attempt count, elapsed time and SQL/API error code. Monitor failed `pg_net` responses and function retries; surface persistent failures in the office rather than swallowing browser retry errors.
6. Measure and bound trigger work under batched status changes. Ensure status-log generation is driven only by actual status transitions, avoid repeated full-timeline scans where a direct append-only event insert can preserve the same audit contract, and ensure a closing-wave bulk update does not dispatch per-app notifications that the batch closing letter already covers. Keep all role/stage enforcement and audit rows intact.

### P1 - Load Shedding and Request Discipline

1. Debounce server-backed search, cancel stale page requests, deduplicate identical in-flight reads, and prevent overlapping poll/focus requests. Jitter background refresh timing so 100+ clients do not synchronize. Avoid broad Realtime subscriptions as a default; evaluate only if polling metrics show it is more efficient under current project limits.
2. Use explicit per-page and per-RPC limits, bounded import/export batch sizes, and capped worker concurrency. Do not add an arbitrary blanket limit to normal authenticated reads/writes; use platform/Auth limits for Auth abuse and application-level controls only for expensive endpoints/import jobs. Never add service-role credentials to browser code.

### P0 - Verification Gate Before Production Seed

1. Add tests for keyset pagination tie boundaries, filters/counts, request cancellation/coalescing, old localStorage migration/quota failure, role/RLS page boundaries, and every importer validator/idempotent rerun/partial-chunk recovery. Extend release tests for partial and repeated batch calls and notification dedupe.
2. Run build, lint, and the full Vitest suite. Apply migrations and deploy only to staging first; verify generated types, client build, and any affected Edge Function deployment before production rollout.
3. Use k6 or equivalent against staging with real authenticated student and Admin/Staff/reviewer JWTs (provision 100+ isolated staging test accounts; do not share tokens or use production users). Ramp at 25/50/100/150+ concurrent sessions, then soak at the target. Exercise paged queues/search, student application lists, page/detail opens, 15-second refresh behavior, statistics, document metadata, exports, and a controlled write/release batch. Test both a just-over-1,000-row dataset and at least 2x the expected seed size; include concurrent reads during a staging import.
4. Proposed release criteria: every row is reachable exactly once across pages with no silent truncation; page totals and database totals reconcile; no RLS leakage; no duplicate applications/files/status events/notifications after retries; no failed or partially visible Submitted cases; p95 paged API latency below 1 second and p99 below 3 seconds at target concurrency; 5xx/timeouts below 0.5%; no sustained 429s, connection/pool saturation, localStorage quota failures, or multi-second main-thread freezes. Revisit these thresholds against measured device/network expectations before the run.
5. Monitor `pg_stat_statements` (calls/mean/max/rows), query plans, Supabase API/Postgres/Storage/Auth/Function logs, database CPU/memory/disk/cache and connections/pool waits, HTTP 429/5xx, function failures/retries, and importer progress. Alert on sustained latency/error/pool saturation; keep structured batch/request IDs and counts only, with no PII. Take a pre-seed backup, run import, reconcile, then enable the normal workflow on production only after all gates pass.
