# ScholarPath AdDU Agents Guide


## Purpose
This repository contains ScholarPath AdDU, a React + Vite scholarship discovery, eligibility matching, Document Vault, application tracking, notification, calendar, and admin review prototype for Ateneo de Davao University.


This file is the operating guide for any future coding agent working in this workspace.


## Source Of Truth Priority
When deciding what to change, use this priority order:


1. The manuscript and its stated research objectives, scope, limitations, terminology, and evaluation design.
2. The actual codebase and its current working behavior.
3. Future enhancements or refactors that are not already supported by the manuscript or the current app.


If the manuscript and the codebase conflict, preserve the manuscript intent first and then make the smallest code change that keeps the app stable.


## Product Context
ScholarPath AdDU is a centralized hybrid web and mobile system for student scholarship discovery and application tracking. The manuscript defines the core system goals as:


- Centralized scholarship discovery across AdDU's financial aid pipelines.
- A Smart Eligibility Checker that evaluates QPI, household income, degree program, and exclusion rules.
- A Document Vault that supports one-time upload and multi-application reuse.
- A notification subsystem for deadline and status alerts.
- Role-based access control for students, Admissions Office administrators, and Department Chairs.
- A student application workspace for filtering, submitting, inspecting, and exporting application reports.
- An Admissions Office workspace for maintaining AdDU internal scholarship catalog entries and coordinating central application review.
- A reusable Document Vault with upload validation, verification states, and application links.
- A deadline calendar supporting scholarship deadlines and student-created reminders.
- Configurable notification channels and reminder timing, with an in-app notification center.
- A polished task-based usability prototype evaluated with ISO/IEC 25010 and SUS.


The manuscript also establishes important scope boundaries that must stay intact:


- The system is discovery, matching, upload, and tracking focused.
- It does not implement actual financial disbursement.
- It does not integrate with the registrar for verified QPI.
- It does not give external scholarship organizations direct administrative access.
- It remains a prototype. Supabase is required for data and authentication; the demo mode, its seeded data, and the fallback login were removed, which reverses the earlier scope statement that the system "must continue to work in demo mode when Supabase is not configured."

## Current Codebase Map
The present implementation is organized as follows:


- `src/App.jsx` is the main state and routing-style coordinator for authentication, app state, theme, profile hydration and saving (`saveProfile`), notification generation, deadline reminders, and view switching. It persists the app state in localStorage under `scholarpath-addu-state` (with a one-time migration from the legacy `scholarpath-addu-demo-state` key).
- `src/pages/` contains the main screens:
  - `LoginScreen.jsx` — Google OAuth accepts personal Google accounts as well as AdDU accounts; do not send a Google hosted-domain (`hd`) restriction. Account creation and password-reset forms accept a general email address.
  - `DashboardView.jsx`
  - `ScholarshipExplorer.jsx` — scholarship discovery with the inline Smart Eligibility Checker on each scholarship card.
  - `ApplicationsView.jsx` — student application filtering, progress, detail modal (requirement checklist, supporting documents, statement, profile snapshot, timeline), and text report export (which includes the supporting documents, each rejection reason, and the full profile snapshot). While an application is `Submitted`, `Under Review`, or `For Verification`, a `Rejected` attached file shows its reason with a `RejectedDocumentReplacer` (pick another vault file or upload a correction into the vault first), and the application card asks for the replacement. A Draft opens the application workspace (`src/components/ApplicationWorkspaceModal.jsx`), a four-step flow: attach each required document from the Document Vault (or upload a new file, which lands in the vault first) and, optionally, other vault files as supporting documents, review the self-reported profile snapshot (everything it lists is sent), write the statement (prefilled from the default scholarship statement in My Profile; the student can reset to it or save the tailored text back as the new default), then certify and submit. External and government-linked entries are tracked only: no checklist and no submit.
  - `DocumentVaultView.jsx` — student document upload, search/filter, verification display, and deletion. A `Rejected` file shows its reason and, when an in-scope application before endorsement still uses it, an action that opens that application's details to replace it. The upload form is attribute-driven: one grouped picker (mirroring the program/course picker) lists each profile attribute with the document types it accepts below it, plus a leading "General documents" group; picking an item chooses the attribute and document type together, and the vault derives the title from the pair, so there is no free-text title and no attribute checklist.
  - `src/pages/admin/` — the Admissions Office workspace, split into one route per function instead of a single monolithic console: `AdminOverview.jsx` (`admin`, the landing route with the review/document/release metrics, the links into each workspace, and the recent application activity feed derived from status logs and timelines), `AdminReviewQueue.jsx` (`admin-review`, the review queue and SOP stage track; opening a Submitted application starts its review, each entry's primary action is Start review / Open review / Review documents, and an entry only badges documents still to verify once its status unlocks them), `AdminScholarshipCatalog.jsx` (`admin-catalog`, AdDU internal scholarship publishing/editing and the required-documents editor; leaving the route with unsaved input asks before discarding), `AdminResultsRelease.jsx` (`admin-release`, recommendation/release actions and the accepted-list export), and `AdminAnnouncements.jsx` (`admin-announcements`, announcement publishing and the published list). Their derivations live in `src/lib/admissionsOffice.js`, and every page shares `src/components/AdminPageHeader.jsx` so the workspace keeps one title surface per page. Document Vault verification happens inside each application's `ApplicationReviewModal`, the shared staff review surface: a fixed header (applicant, status, `SopStageTrack`, documents-verified count), Overview / Documents / Profile snapshot / History tabs, and one sticky action bar that renders one button per transition from `getNextApplicationStatuses(status, role)` apart from the automatic `AUTOMATIC_STAGE_STATUSES` moves, labelled by `getStageActionLabel()` (the interview date/panel and sub-committee note fields sit in that bar beside their action). Its Documents tab is hidden until the application reaches `For Verification` (stage gate `areDocumentsReviewable()`, visibility `areApplicationDocumentsVisible()` which keeps a Rejected application's files readable), and the footer explains the SOP step-3 gate instead, beside the `Continue to verification` action that opens the file queue in place; once unlocked it lists the required submissions and supporting files on the left and, from the `lg` breakpoint, previews the selected file inline (`DocumentPreview` from `DocumentPreviewModal.jsx`) beside its `DocumentVerificationItem` details (what the file proves, the value declared at upload, and the outdated state); below `lg` the preview opens in its own modal. The Verified/Rejected actions are Admissions-Office-only and Department Chairs see the same pane read-only. There is no standalone document list, so a Pending file that no queued application relies on is not reviewed until the student submits it with an application.
  - `DepartmentReviewView.jsx` — department-scoped Chair review queue; Chairs can flag eligible submitted/in-review applications for central validation and endorse applications in `For Verification`.
  - `CalendarView.jsx`
  - `SettingsView.jsx`
  - `ProfileView.jsx` — My Profile for every role: section menu, completeness metric, and the Overview, Personal information, Address, Family details, Academic profile, Household and financial aid, Eligibility background, and Account security sections. Address, Family details, Academic profile, Household and financial aid, and Eligibility background are student-only. Personal information carries the short bio for every role plus a student-only default scholarship statement (stored as `essay`), an optional template that prefills each new application statement and is not counted toward profile completeness. The Overview presents the profile-completeness checklist and, for students, the student-only Documents for applications card. Its completeness checklist (`getProfileCompleteness()` in `src/lib/profile.js`) follows `getStandingRequirements()`: an item that does not apply to the student's standing is left out rather than counted as done, so an incoming first-year is asked for the senior high school general average and strand instead of an AdDU student number and QPI. Student items are grouped into "Needed to apply" (the answers the application gate reads and the submission snapshot freezes) and "Additional details"; staff see only their name and mobile number. Below it, the student-only "Documents for applications" card (`getDocumentChecklist()` in `src/lib/applicationRequirements.js`) merges the required documents of the open AdDU internal scholarships for the student's standing, reads each against the whole Document Vault (a non-rejected file counts, as for submitting), and links to the vault with the document type preselected (`getRequirementUploadPreset()`); it also shows whether a default scholarship statement is saved. Each editable section has an independent draft, validation, save, and discard flow; navigation prompts before discarding unsaved changes.
- `src/components/` contains shared UI building blocks (`ui.jsx`: `Button`, `Card`, `FormField`, `SettingToggle`, `ModalShell`, and related primitives), the reusable `ReasonModal` for required recorded reasons, modal/page-part helpers, notification cards, announcements, the `NotificationDropdown` center, the first-login `AcademicProfileModal`, and the My Profile section forms in `ProfileSections.jsx` (built on its `useSectionForm` draft/validate/save hook).
- `src/lib/` contains the domain logic, formatting helpers, authentication and profile helpers (`auth.js`), eligibility rules, role-aware application transitions (`getNextApplicationStatuses(status, role)` in `constants.js`), local persisted state (`appState.js`), academic-program taxonomy, profile field definitions and validators (`profile.js`), Document Vault storage helpers (`documentStorage.js`), and Supabase setup. The scholarship catalog is read from the Supabase `scholarships` table via `src/lib/supabaseData.js`; the Admissions Office catalog form saves eligible AdDU internal entries through `createSupabaseScholarship()` / `updateSupabaseScholarship()`; the local persisted state (theme, notification preferences, custom deadlines, and onboarding flags) lives in `src/lib/appState.js`, which starts from empty defaults because Supabase is the authoritative source for applications, documents, notifications, announcements, and department reviews; and academic programs are loaded from the Supabase `academic_programs` table via `loadSupabaseAcademicPrograms()` (in `src/lib/supabaseData.js`), with `src/lib/academicPrograms.js` (value/label/department/category) as the offline reference fallback.
- `supabase/schema.sql` is the reference schema for fresh Supabase projects. For an existing/deployed project, add and apply a migration under `supabase/migrations/` rather than re-running the full schema; keep the reference schema aligned with those migrations.
- `supabase/functions/` holds the email and SMS delivery Edge Functions described under Email And SMS Notification Delivery.
- `src/tailwind.css` is the primary Tailwind entry point and contains the shared theme primitives.
- `src/styles.css` contains component-specific CSS, browser behavior, pseudo-elements, keyframes, and rules that are not practical as utilities.

## Editing Principles
Follow these rules when making changes:


- Prefer the smallest change that solves the task.
- Reuse existing shared components, helpers, and data shapes instead of duplicating logic.
- Supabase is the required backend; do not reintroduce an offline demo mode, seeded data, or a fallback login.
- Preserve backward compatibility with stored state in localStorage, including the one-time migration from the legacy demo key.
- Fail cleanly with a clear "not configured" message when the Supabase environment variables are missing, instead of silently entering any offline mode.
- Do not introduce new dependencies unless they clearly solve the task better than the current stack.
- Do not remove or rewrite manuscript-aligned terminology just to make the code more generic.
- Avoid unnecessary refactors that change behavior, layout, or data shape.
- Treat `applications`, `documents`, `notifications`, `announcements`, `customDeadlines`, `notificationPreferences`, `profileDraft`, and `theme` as persisted state domains; add compatibility defaults when extending them.
- Keep file-upload behavior safe: the file bytes live in a private Supabase Storage bucket (`documents`), and the `documents` row records the object path in `storage_path`. Students manage only their own folder (`documents/<auth.uid()>/<documentId>/<file>`), the Admissions Office reads every document, and a Department Chair reads documents owned by students in the chair's department; viewing always goes through a short-lived signed URL. The bucket and its storage RLS policies come from `supabase/migrations/20261009000000_add_document_storage.sql`. The `protect_document_review_fields` trigger (`20261013000000_add_document_attested_values.sql`, extended by `20261021000000_replace_rejected_application_documents.sql`) keeps the review fields staff-owned: a student's insert is forced to `Pending` with a server `uploaded_at`, and a student cannot change `verification_status`, `rejection_reason`, `verification_decided_at`, `linked_attributes`, `attested_values`, `uploaded_at`, or `owner_id` afterwards.


## Domain Rules
These rules come from the manuscript and should guide implementation details:


- Eligibility matching should honor QPI, income, degree program, active status, deadline state, and exclusion logic.
- The academic requirement branches on year standing, mirroring `getStandingRequirements()` in `src/lib/profile.js`: enrolled students (1st–5th year) are matched on the collegiate QPI, while incoming first-years are matched on their senior high school general average. The Admissions Office internal catalog stores both floors (`minimum_qpi` and `minimum_shs_average`), and `getAcademicRequirement()` in `src/lib/eligibility.js` is the single source the application gate, the general-pool evaluator, the fit score, and the requirement chips read. Honors (Jubilee) and work-study (Student Assistant) declare no academic floor, so they show no academic requirement chip.
- Specific exclusions must override broad inclusions.
- Jubilee Scholarship eligibility is not restricted to incoming first-year students; retain its official Valedictorian/Salutatorian standing and graduating-class size criteria.
- Student Assistant (SA) / Working Scholar eligibility is open to students across all academic programs and must not be blocked by degree-specific catalog metadata.
- Scholarship discovery should support faceted filtering and fast search over the current taxonomy.
- Document handling should behave like a normalized vault where the same file can be attached to multiple applications.
- Notifications should remain event-oriented; the scheduled Edge Function is the delivery path, while the in-app center reads the local and server rows.
- Role-based access should preserve student, central Admissions Office administrator, and department-scoped Department Chair boundaries; never give the central administrator Dean-like scope under a department role.
- My Profile editing must keep the same boundaries: students edit their academic, household, and eligibility background fields, while Admissions Office administrators and Department Chairs edit only their name, mobile number, and bio. Department assignment is never self-editable because it scopes the Department Review queue; `saveProfile` in `App.jsx` enforces this with `STAFF_EDITABLE_FIELD_KEYS`, not only the UI.
- Profile QPI and household income are self-reported. They can optionally be verified by the Admissions Office against Document Vault proof, so never describe them as Registrar-verified and never imply a registrar integration.
- Year standing is the single student control (Incoming 1st year, then 1st–5th year); `applicantType` and `yearLevel` are derived from it for the eligibility engine and stored alongside it. `getStandingRequirements()` in `src/lib/profile.js` is the single source for which fields apply, and the onboarding modal, My Profile Academic profile, validators, and routing gates all read it. An incoming first-year reports ranked program choices and senior high school strand/general average instead of an AdDU student number and collegiate QPI, so profile completeness and onboarding skip those continuing-student fields.
- An application must not be submittable "whenever". Each AdDU internal catalog entry lists its required documents in `scholarships.required_documents` (`{ id, label, documentTypes, standing: 'all' | 'incoming' | 'continuing' }`), edited by the Admissions Office in the catalog form (`RequiredDocumentsEditor`) and defaulting per rule family to `DEFAULT_REQUIRED_DOCUMENTS` in `src/lib/applicationRequirements.js` (keep it identical to the backfill in `20261012000000_add_application_requirements.sql`). `getApplicationReadiness()` is the single readiness check for the workspace, the submit handler, and the staff review modal: every requirement for the student's standing needs a non-rejected attached vault file (Pending is enough; verification stays at `For Verification`), plus a statement, the certification checkbox, an open deadline, and a passing eligibility gate. The `enforce_student_application_update` trigger repeats the gate server-side, limits students to creating Drafts and moving `Draft` → `Submitted`, and freezes submitted rows; `protect_submitted_application_documents` stops a student from deleting a vault file a submitted application relies on; students may change `application_documents` links only while the application is a Draft, except that a Rejected file may be replaced before endorsement (see the replace-in-place rule below).
- Submission stores `statement`, `certified_at`, and the frozen `profile_snapshot` (`buildProfileSnapshot()`: self-reported values with their derived Document Vault verification badges, never Registrar-verified) on the application. Snapshot version 2 keeps the original fields (name, student number, program, department, year standing, QPI or senior high school general average, household income, citizenship) and adds the `eligibility` answers (academic standing, honors rank, graduating class size, the three exclusion flags, and for an incoming first-year the strand and ranked program choices), `background` (IP community, PWD, employment), `personal` (civil status, religion), `address`, and `family` groups; the default scholarship statement (`essay`) is never copied. `getProfileSnapshotSections()` is the single labelled view of a snapshot that the workspace, the student's detail modal and export, and `ApplicationReviewModal` (Admissions Office and Department Chairs alike) render; a snapshot without `version` was submitted earlier and shows only the original fields. Students may also attach optional supporting documents: any of their own non-rejected vault files whose type matches no requirement for their standing. `getApplicationReadiness()` returns them as `supportingDocuments`; they never gate submission and use the same `application_documents` links (Draft-only, except a rejected-file replacement before endorsement). Tell the student what is shared: the workspace Profile snapshot step lists every group expanded, the Review and submit step states that the documents, statement, and full profile snapshot go to the Admissions Office and the Department Chair, and the certification checkbox doubles as the student's consent to that sharing. My Profile (section descriptions, the Religion hint, the completeness group notes) and the Document Vault upload card say the same; keep these notices aligned when the snapshot or the staff document access changes. Application ids are real uuids generated client-side and passed to `createSupabaseApplication()`, like vault documents.
- Application progress should remain status-driven (`Draft`, `Submitted`, `Under Review`, `For Verification`, `Endorsed`, `Interview`, `Recommended`, `Approved`, `Released`, and `Rejected`). Submission and each status transition must persist a trackable event in the application's `timeline`, then invoke the server-side application-status notification after the status write succeeds.
- Documents should expose verification states (`Pending`, `Verified`, and `Rejected`) and remain reusable across applications through attached document IDs. Each decision stamps `documents.verification_decided_at` (`require_document_rejection_reason`, `20261021000000`) so a repeat rejection of the same file gets its own notification key.
- Student recovery from a rejected Document Vault file is replace-in-place, and only before endorsement. While the application is `Submitted`, `Under Review`, or `For Verification` (`DOCUMENT_REPLACEMENT_STATUSES` in `src/lib/constants.js`), the student may swap a `Rejected` attached file for another own, non-rejected vault file — or a new upload that lands in the vault first. `replace_rejected_application_document(p_application_id, p_old_document_id, p_new_document_id)` (`20261021000000`, granted to `authenticated` only) re-checks ownership, the application status, that the old file is attached and `Rejected`, that the new file is the caller's and not already attached, and that it is the same `document_type` or shares one `required_documents[].documentTypes` entry. It deletes and inserts the `application_documents` link in one transaction and never touches the application row, so `enforce_student_application_update` is unaffected and the status stays the same. The replacement arrives `Pending`; the application may not advance until every attached file is `Verified`. The unlinked rejected file is then deletable through `protect_submitted_application_documents`, which only guards files an application still relies on. The client mirrors this with `getReplaceableRejectedDocuments()` / `getReplacementOptions()` in `src/lib/applicationRequirements.js`, `replaceRejectedDocument()` in `App.jsx`, `replaceSupabaseApplicationDocument()` in `src/lib/supabaseData.js`, and `RejectedDocumentReplacer` in `src/components/ApplicationParts.jsx`, which the student's application detail modal renders under each `Rejected` file. No `timeline` entry is written for a replacement because a student cannot write a submitted row; staff see the new `Pending` file and the queue's files-to-verify badge.
- Document Vault files are stored in the private Supabase Storage `documents` bucket; `documents.storage_path` holds the object key and `documents.id` is a real uuid generated client-side, so `application_documents.document_id` can reference it. Viewing always uses a short-lived signed URL (`getSupabaseDocumentUrl`), never a public link.
- Profile attribute verification is informational and derived, never stored separately: a vault document declares the attribute(s) it proves via `linkedAttributes` (client) / `documents.linked_attributes` (Supabase), and `deriveAttributeVerifications()` in `src/lib/verification.js` maps each `VERIFIABLE_ATTRIBUTE_OPTIONS` key to `Unverified` / `Pending` / `Verified` / `Rejected` / `Outdated` from those links. Verifying the document in the Admissions Office console verifies the linked attributes; it must never block eligibility matching or applying.
- A proof records the normalized declared value it was uploaded to prove in `attestedValues` / `documents.attested_values` (`normalizeAttestedValue()` in `src/lib/profile.js`). Only current proofs count toward an attribute: a proof is outdated when the profile value no longer matches its attested value, or when an `annual` attribute (QPI, household income) was uploaded in an earlier academic year (June start, `getCurrentAcademicYear()`). An attribute whose every proof is outdated reads `Outdated`; the document's own status is never reset, and changing the value back makes the proof current again. Documents with no attested value (uploaded before the column existed) count as current. The Document Vault flags outdated proofs and filters on them, and the Admissions Office card shows the value declared at upload. The student is warned twice: each My Profile section shows an inline notice before saving a change that would outdate a proof (`getNewlyOutdatedAttributes()`), and an in-app notification center row is added once per stale state (`getOutdatedAttributeAlerts()`, source key `outdated-proof-<key>-value-<value>` or `outdated-proof-<key>-<academicYear>`, gated on `inAppEnabled` and on the workspace having loaded). These are client-side only; the server does not email or text outdated-proof alerts.
- Custom calendar deadlines must be future-facing, persisted locally, removable, and eligible for the configured 7-day, 3-day, and 1-day reminders. They are also mirrored to the Supabase `custom_deadlines` table with the client id stored verbatim (for example `custom-<uuid>`), so the scheduled function can email the same reminder the client generates locally.
- In-app notification creation must respect `notificationPreferences.inAppEnabled`; generated reminders must use a stable source key so they are not duplicated on each render.
- Application-status in-app rows are written by `notify-application-status` using the stable `application-status-<applicationId>-<status>` source key; client-generated local in-app rows remain for deadline reminders and other local events.
- Server-side delivery must honor `profiles.notification_preferences` per channel and per reminder, and must record only real deliveries in `notification_email_log` so a reminder reaches a student at most once while a skipped or failed send stays unlogged and retryable. See Email And SMS Notification Delivery.
- Scholarship catalog management through the Admissions Office console is limited by the role and RLS to AdDU internal entries (`category = 'Internal Endowment'`, `is_external = false`, `rule_family` in `general-pool`, `honors`, or `work-study`). Government-linked and external entries remain outside this management path; catalog eligibility is not an award or disbursement decision.
- Application stage authority is role-scoped: Department Chairs may flag `Submitted` / `Under Review` applications for central validation and endorse `For Endorsement` applications; central verification, the hand-off to endorsement, and subsequent SOP actions belong to Admissions Office administrators. Enforce this in the role-aware transition map, `App.jsx` guards, and the department-chair RLS policies; the Chair's review remains limited to their assigned department. `getNextApplicationStatuses(status, role)` in `src/lib/constants.js` is the single source of stage authority; `changeApplicationStatus` reads it instead of a second inline map.
- Opening an application in the Admissions Office starts its review: `AdminReviewQueue` moves a `Submitted` application to `Under Review` once, in the background, so the reviewer never presses a separate "Mark under review" button and the student is notified once through `application-status-<applicationId>-<status>`. `Under Review` therefore lives in `AUTOMATIC_STAGE_STATUSES` (`src/lib/constants.js`) and is never rendered in the action bar; it stays in the role map only as the guard for that automatic write and as the fallback that still lets a Submitted application continue straight to verification when the write did not land.
- Document review is gated to the verification stage. `areDocumentsReviewable(status)` (`src/lib/applicationRequirements.js`) is true only from `For Verification` on: `ApplicationReviewModal` hides its Documents tab before that (the Admissions Office gets `Continue to verification` in the action bar, which keeps the modal open and switches it to the now-unlocked Documents tab instead of closing it), and `getDocumentsAwaitingReview()` counts only Pending files attached to applications at verification so the overview and queue metrics match what the stage allows. Department Chairs see the same Documents pane read-only once the application reaches verification and endorse after it has been sent to endorsement with every attached file Verified.
- The endorsement hand-off is explicit and belongs to the Admissions Office: at `For Verification`, once every attached file is Verified, the admin's action bar offers **Send to endorsement** (`getStageActionLabel('For Endorsement', 'admissions_office')`) and moves the application to the stored `For Endorsement` status. The Department Chair then sees it in the department queue as *awaiting endorsement* and records the decision with **Endorse** (`For Endorsement` → `Endorsed`). The Chair can no longer endorse straight out of `For Verification`, so the admin's hand-off is the only way into step 4, and `DepartmentReviewView` enables the endorse button only on `For Endorsement` rows whose attached files are all Verified.
- The stored `Endorsed` status is displayed as **Endorsement** (the SOP phase) through `getApplicationStatusLabel()`, defined once in `supabase/functions/_shared/applicationStatus.js` so the app, the status email, the SMS text, and `notify-application-status` cannot disagree. The stored value stays `Endorsed` — the status check constraint, the chair RLS policies, `enforce_document_verification_before_progress`, and the append-only status log all read it — so only the display translates: badges, the SOP stage track, the status history, both exported reports, and the student guidance read the label. `For Endorsement` is a separate stored status and displays as itself. The Edge Function must be redeployed (`supabase functions deploy notify-application-status --no-verify-jwt`) for new notification wording to go live.
- The Admissions Office action for `Submitted` / `Under Review` → `For Verification` is **Continue to verification**; the Department Chair keeps the role-scoped **Flag for central validation** label. `changeApplicationStatus` awaits the Supabase write, returns `{ ok }` / `{ error }`, records a "Continued to document verification. Attached files are queued for Admissions Office review." timeline event, and only updates local state and sends the notification retry after the write succeeds. `AdminReviewQueue` confirms the transition with a dismissible banner, and the review modal stays open on the newly unlocked Documents tab so the attached Pending files are one action from the stage change. `getApplicationStatusGuidance()` supplies the student-facing next-step copy in `ApplicationsView`, and `notify-application-status` uses `describeApplicationStatusUpdate()` so the `For Verification` email and in-app row explain that the documents are with the Admissions Office and when the student will hear next.
- A status change is recorded in the append-only `application_status_log` (`20261014000002`), written by an after-update trigger with `actor_id = auth.uid()` and `actor_role = current_profile_role()` (or `system` for a service-role job); it is readable but never editable or deletable. `ApplicationReviewModal` shows this log as the status history — the reviewer's name for staff, the role for a student, and "System" for a system move — and falls back to the legacy `applications.timeline` only when the log is empty.
- An application may only advance to `For Endorsement`, `Endorsed`, `Interview`, `Recommended`, `Approved`, or `Released` once every attached Document Vault file is `Verified` (manuscript 3.3.3). `getDocumentVerificationReadiness()` / `isApplicationVerifiedForEndorsement()` (`src/lib/applicationRequirements.js`) disable the reviewer's forward actions and explain why, and `enforce_document_verification_before_progress` (`20261014000000`) enforces the same rule in the database. `Rejected` is always allowed.
- A Verified Document Vault file that an application has already relied on past `For Verification` cannot be un-verified (`protect_verified_documents_on_progress`, `20261014000004`): the staff must revert the application first, otherwise the document-verification gate would strand it. Re-verifying, or changing any other column, is unaffected.
- Only the three Appendix A tracks may be applied to. `isAdduInternalProgram()` (title-based, `src/lib/eligibility.js`) is the single in-scope predicate used wherever an application can be started, continued, or submitted; `isInternalScholarship()` remains only the looser catalog-listing helper and must not gate the lifecycle. `is_addu_in_scope_track()` (`20261014000001`) enforces the same title rule inside `enforce_student_application_update`, so an unrelated internal catalog entry (for example a donor endowment stored as `general-pool`) is tracked-only, exactly like an external program. External and government-linked entries are unaffected and stay trackable.
- The single persisted app record is scoped to the signed-in user by `ownerId`. Sign-out resets to `createFreshState()` in `src/lib/appState.js` (keeping only device preferences such as `theme`), and `mergeNotifications`, `mergeCustomDeadlines`, `backfillLocalDeadlines`, and newly created deadlines/reminders are owner-scoped, so a shared browser never carries one user's notifications, reminders, applications, documents, or profile draft into the next session (`tests/sessionIsolation.test.js`).
- The app should continue to feel like a prototype aligned with the study, not a generic scholarship portal.


## Email And SMS Notification Delivery
Notifications stay event-oriented, and delivery runs through Supabase Edge Functions rather than the browser:

- `process-deadline-reminders` is invoked daily at 07:00 Asia/Manila by pg_cron + pg_net (`supabase/migrations/20261005000001_schedule_deadline_reminders.sql`, with the reference block at the bottom of `supabase/schema.sql`). It evaluates the reminder rule on the Manila calendar, writes the in-app row, emails through Resend, texts through iprogSMS, and records the delivery in `notification_email_log`. It runs with `verify_jwt` disabled and authenticates the scheduled caller against `REMINDER_CRON_SECRET` by exact value; a signed-in user's JWT is also accepted for on-demand runs. Never point this endpoint at the anon key.
- `notify-application-status` is fired from the database by an after-update trigger (`supabase/migrations/20261014000003_notify_application_status_from_database.sql`, with the reference block at the bottom of `supabase/schema.sql`) whenever `applications.status` changes. The trigger is the **primary delivery path**, and the app still calls it after a successful status write as a retry for a tab that closed first. Because the two can run for the same change at almost the same moment, the function sends SMS **only for the database caller** (`isTrustedDatabaseCaller`): email dedupes through a Resend idempotency key and the in-app row through its source key, but SMS has neither, so the browser retry covers only the in-app and email channels and preserves whatever the database path recorded in the ledger. Like `process-deadline-reminders`, it runs with `verify_jwt` disabled because the database caller presents the shared `REMINDER_CRON_SECRET` (the platform JWT check rejects service role keys); it authenticates that secret by exact value inside the function, and a signed-in user's JWT is still validated for the browser path. It re-reads the application, recipient, and caller role server-side so the request body cannot spoof the recipient, and it allows only the trusted database caller, the Admissions Office administrator, the Department Chair for that student's department, or the student who owns the application. For a database-triggered call the message actor is read from `application_status_log.actor_role`. It writes the in-app row with `source_key = application-status-<applicationId>-<status>` and an upsert on `(profile_id, source_key)`, so the trigger and the client retry send at most one in-app row; `inAppEnabled` controls that channel. Email and SMS are handled independently and tracked by `email_status` / `sms_status` in `notification_email_log`, so already-delivered channels are skipped while failed or skipped sends remain retryable.
- `notify-document-verification` tells the student when the Admissions Office verifies or rejects one of their Document Vault files. It follows the same pattern: the database trigger (`20261021000001_notify_document_verification_from_database.sql`) is the **primary delivery path**, and `changeDocumentStatus` in `App.jsx` calls it after the successful write as the idempotent retry. It runs with `verify_jwt` disabled, accepts the exact `REMINDER_CRON_SECRET` for the database caller or a signed-in Admissions Office JWT, re-reads the document, its owner's profile and `notification_preferences`, and the applications that attach the file, and dedupes on `source_key = document-verification-<documentId>-<status>-<epoch(verification_decided_at)>` so a file rejected again after a reset notifies again. A `Rejected` decision goes to in-app (`inAppEnabled`), email (`emailEnabled`, with a Resend idempotency key) and SMS (`smsEnabled`, **database caller only**, preserving the browser retry's ledger like the status function); every message carries the recorded reason and tells the student to replace the file from the application's details. A `Verified` decision is in-app only, so a multi-file application does not send a burst of emails and texts. Deploy it with `supabase functions deploy notify-document-verification --no-verify-jwt`; it uses the same `RESEND_*`, `APP_SITE_URL`, `REMINDER_CRON_SECRET`, and `IPROGSMS_*` secrets.
- `send-test-email` backs Settings -> Email delivery test and only ever sends to the signed-in caller; `send-test-sms` is its SMS counterpart and text messages only the caller's own `profiles.phone` number (echoed back masked).
- Shared, dependency-free modules live in `supabase/functions/_shared/`: `email.js` (Resend-compatible table HTML, plain-text alternatives, and the delivery-preference checks), `reminders.js` (the reminder math shared with `src/App.jsx`), `resend.js` (the minimal email fetch client), and `sms.js` (iprogSMS client, Philippine mobile normalization, and SMS text renderers). They are plain JavaScript so Deno, the vitest suite, and the client bundle can all import them (for example, `validateMobileNumber` in `src/lib/profile.js` reuses `formatPhilippineMobile` for the onboarding modal and My Profile, and Settings reuses `maskPhilippineMobile`).
- Delivery is opt-in per channel and per reminder. `profiles.notification_preferences` is the only server-side input: the in-app deadline row needs `inAppEnabled` plus the matching `deadlineReminders` offset, the email needs `emailEnabled` plus the same offset, and the SMS needs `smsEnabled` plus the same offset and a normalizable `profiles.phone` value. Status notifications honor `inAppEnabled`, `emailEnabled`, and `smsEnabled`; in-app rows dedupe on the unique `notifications(profile_id, source_key)` key, while email and SMS deliveries are independently deduped/retried through their channel statuses in `notification_email_log`. `isInAppEnabledForUser()` in `_shared/email.js` defaults in-app status alerts to enabled unless explicitly disabled.
- `notifications.channel` is constrained to `SMS` / `Email` / `In-app`, so carry the deadline kind in the notification title and body instead of adding a channel value.
- Email requires the verified Resend sending domain and the Edge Function secrets (`RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `RESEND_FROM_NAME`, `APP_SITE_URL`, `REMINDER_CRON_SECRET`); SMS requires `IPROGSMS_API_TOKEN` (with optional `IPROGSMS_PROVIDER`, the gateway's `sms_provider` 0/1/2 flag). They are server-side only and must never carry a `VITE_` prefix. A send only happens when the Supabase workspace is loaded, and either gateway may be left unset without breaking the app (sends are skipped, never thrown).
- The email CTA links use `?view=calendar`, `?view=applications`, and `?view=settings`, but the app does not read a `view` query parameter yet, so a recipient lands on the role's landing view. Do not describe those links as deep links until `App.jsx` handles the parameter.
- iprogSMS constraints: a 200 response confirms queue-accept (`message_id`) only — there are no delivery webhooks, so ledger rows describe queue-accept rather than confirmed carrier delivery (poll-only status via `GET /sms_messages/status`). Globe, TM, DITO, and GOMO recipients use the shared `iprogSMS` sender; Smart and TNT require a purchased custom sender name.

The other server-side mirrors are `custom_deadlines` (one row per student-created deadline, id stored verbatim) and `notification_email_log` (the service-role delivery ledger). Keep the local and server shapes identical so the two never disagree.
- `notifications.source_key` is an additive stable idempotency key, unique per `(profile_id, source_key)`; the application-status source key is `application-status-<applicationId>-<status>`. Existing Supabase projects receive it from `20261010000000_add_application_notification_source_key.sql`, and `supabase/schema.sql` must stay aligned.

Submission and status events should remain part of the application record, not synthetic client-only notifications.
- `saveScholarship` in `App.jsx` persists catalog forms through `createSupabaseScholarship()` / `updateSupabaseScholarship()` in `src/lib/supabaseData.js`; `scholarshipToRow()` forces these UI-managed entries to be non-external. The database RLS policy is in `20261010000001_limit_chair_transitions_and_manage_internal_scholarships.sql`.
- `loadSupabaseWorkspace()` adds `ownerName` and `ownerDepartment` to loaded document records for Admissions Office document review; these labels come from the profiles visible to the staff query.
- The workspace also returns a compact `students` directory for visible profiles. Admissions Office document verification uses it to compare linked QPI and household-income proof against the student's declared profile values; owner labels fall back to the document's loaded owner fields.
- Application rejection requires a recorded reason through `ReasonModal`; it is saved to the application's timeline.
- Document Vault rejection also requires a recorded reason: the Reject action in `ApplicationReviewModal` opens `ReasonModal` with the preset `documentRejectionReasons` dropdown (`src/lib/constants.js`) and optional notes (required for "Other"; stored as "<reason> — <notes>"), and `changeDocumentStatus` in `App.jsx` saves it through `updateSupabaseDocumentStatus(id, status, reason)` to `documents.rejection_reason` (`20261020000000_add_document_rejection_reason.sql`). The `require_document_rejection_reason` trigger refuses a move into `Rejected` without a reason and clears the reason when the file leaves `Rejected`; `protect_document_review_fields` keeps the column staff-owned. `DocumentRejectionReason` (`ApplicationParts.jsx`) shows the reason in the review pane, the Document Vault card, and the application workspace. A file rejected before the column existed has no reason and shows none. Department Chairs flag eligible `Submitted` / `Under Review` applications by moving them to `For Verification`, which records the action in the timeline and sends the normal status notification after a successful status write.
- Application-status in-app notifications are written by `notify-application-status` after the Supabase status write succeeds. Do not add synthetic client-side application-status notifications; staff changes belong in application timelines, and student alerts use the server's stable source key.
- `validateFinancialSection()` does not require `hasActiveGovernmentGrant`; that account/profile field remains supported, but it is not a required financial-section answer.
- Profile data has three local homes. `authUser` holds the account fields (`fullName`, `phone`, `bio`, `studentNumber`, `degreeProgram`, `department`, `qpi`, `householdIncome`, `hasActiveGovernmentGrant`), mirrored to the core `profiles` columns. `profileDraft` holds what the Smart Eligibility Checker reads, including the extended attributes listed in `ELIGIBILITY_ATTRIBUTE_KEYS` (`src/lib/profile.js`) — which now also carry the ranked `programChoice2` / `programChoice3` (an incoming first-year's 2nd and 3rd program choices) and the self-reported `ipCommunity`, `pwd`, and `employed` answers — plus the descriptive fields listed in `PROFILE_DETAIL_KEYS` (religion, civil status, address, country, family details, and the default scholarship statement `essay`). The eligibility attributes are mirrored to `profiles.eligibility_attributes`; the descriptive fields are mirrored to `profiles.profile_details`. Save through `saveProfile` / `updateProfileFields`, which write only the keys present on the patch, and keep the key lists in `src/lib/profile.js` as the single source.
- `profiles.bio` and `profiles.eligibility_attributes` come from `supabase/migrations/20261005140000_add_profile_details.sql`; `profiles.profile_details` comes from `supabase/migrations/20261008000000_add_profile_details_json.sql`. `getProfileDetails()` reads them in separate queries and `updateProfileFields()` writes each group in its own statement, reporting `detailsSynced: false` when a column is missing, so a project with a migration pending still signs in and saves the rest. Do not add these columns to the `getUserProfile()` select: a missing column would fail the whole query and reopen the onboarding modal.
- Citizenship, IP community, PWD, and employment status are self-reported and verifiable through the Document Vault (`VERIFIABLE_ATTRIBUTE_OPTIONS`), like QPI and household income. Verification stays informational and never blocks eligibility matching or applying. Class size remains part of the Eligibility background section and the Jubilee honors criterion.
- Saving a QPI through `updateUserProfile` or `updateProfileFields` also upserts the current academic year in `annual_qpi_records`.
- New localStorage state must be merged with defaults so older saved sessions remain loadable; do not assume `customDeadlines` or notification preferences exist in older records.
